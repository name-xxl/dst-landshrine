### ⚠ 改代码前必读：两个运行环境的区别

饥荒的 mod 代码跑在**两个不同的 Lua 环境**里，读全局名的规则不一样。踩过一次坑，记在这里：

| 文件 | 运行环境 | `GLOBAL` 可读吗 | 能直接读的原版全局 |
|---|---|---|---|
| `modmain.lua` | mod 环境 | **是**（`GLOBAL` 就是 `_G`） | 要用 `GLOBAL.xxx` 访问 |
| `scripts/` 下的所有文件（被 `require` 的模块、prefab、component） | 游戏环境（`_G`） | **否，会直接报错** | 可以，例如 `TheWorld`、`GROUND`、`print` |

原因：原版 `scripts/strict.lua` 给 `_G` 装了严格检查，读取**未声明的全局名**会抛
`variable 'X' is not declared`（mod 环境专有的 `GLOBAL`、以及运行时新建的全局名都属于未声明）。

所以：
- `scripts/` 下的文件**不要**出现 `GLOBAL` / `_G`；需要外部依赖就让 `modmain` 注入
  （见 `landshrine_config.lua` 的 `Init()`：GROUND、TheWorld、日志函数、调试开关都是注入的）。
- `modmain` 里访问原版全局**必须写 `GLOBAL.xxx`**！mod 环境里裸读原版全局**不会报错、只会得到 nil**，
  一调用就是 `attempt to call global 'X' (a nil value)` 直接崩游戏（踩过：`GetGameModeProperty`）。
  注意两类环境的失败模式正好相反，很容易混：
  | | 裸读原版全局 | 裸读未声明的自定义名 |
  |---|---|---|
  | `modmain.lua`（mod 环境） | 静默得到 **nil**，调用即崩 | 静默 nil |
  | `scripts/` 下的文件（游戏环境 `_G`） | 正常可读 | **strict.lua 直接报错** |
- 新增 `modmain` 专用的全局名可以直接赋值（如 `LandShrineDebug = {...}`，成为 mod 环境变量），
  但**只给控制台/调试用**，不要在 `scripts/` 里读它。
- **同样不能直接用原版里以 `local` 定义的辅助函数**。典型翻车案例：照着原版写
  `FindWalkableOffset(..., NoHoles)`，但 `NoHoles` 是 `componentutil.lua` 里的局部函数，
  mod 读到它就报 `variable 'NoHoles' is not declared`，而且错误发生在动作执行链内部，
  表现是**玩家卡住、随后掉线**。原版里凡是 `local function` 的辅助都别直接抄调用。

`tools/lua_check.py` 会把上面三条规则都当成自动检查项跑（`GLOBAL`/`_G` 误用、原版局部名误用、
modmain 裸用原版全局名）。

## 2. 装进游戏

mod 必须位于游戏安装目录的 `mods/` 下才会被识别。**做法：把 `landshrine` 整个文件夹复制到**

```
D:\SteamLibrary\steamapps\common\Don't Starve Together\mods\
```

即得到 `...\mods\landshrine\modinfo.lua` 这样的结构。

> 注意是**复制**而不是剪切/移动：移动会把工作目录里的源码搬走，之后改代码就没有源头了。
> 想让"改完立即生效"，用下面的开发用目录联接，或者每次改完重新复制一遍。

然后在游戏里启用：

1. **先重启游戏**（饥荒只在启动时扫描 `mods` 目录，运行中新建的文件夹不会出现在列表里）。
2. 主菜单 → **模组** → 切到 **「服务器模组」** 标签页（本 mod 的 `client_only_mod = false`，所以归在服务器模组，不在「客户端模组」页）→ 找到「土地庙传送」→ **启用** → **应用**。
3. 服务器模组是**跟着存档保存**的：新建世界时在创建流程的模组页勾选即可；建议**用新档测试**（旧档没有地形槽位相关的数据）。
4. 因为 mod 含客户端逻辑（`all_clients_require_mod = true`），联机时**所有客户端都要有这个 mod**。本地 mod 不会自动下载，别人也得拿到这个文件夹（或以后发布到创意工坊）。

## 3.5 土地庙交互 & 缩地（地图点选传送）怎么用

**交互**（右键庙）：

| 庙的状态 | 右键显示 | 效果 |
|---|---|---|
| 未激活 | **上香** | 播放激活动画、变成已激活；**不打开地图**（让你先看到激活过程） |
| 已激活 | **上香** | 状态不变，**约 0.5 秒后自动打开世界地图** |

也就是说：**第一次上香只管激活**；之后再走到已激活的庙旁右键一下，地图自己就开了，不必再按 M。

**传送**：

1. 站在任意一座**已激活**的土地庙旁边（12 格内）。
2. 地图打开后，**已激活的庙会显示图标，并且穿雾可见**（未激活的庙只有普通建筑图标、且只在自己探索过的区域显示）。
3. 把光标移到想去的庙图标附近（8 格内），此时**右键 = 传送**。
4. 传送成功，地图自动关闭。

规则与分工：

- **客户端**负责"给不给这个动作"：只在「你人在已激活的庙旁」且「光标附近有庙图标」时才提供传送动作——所以不会有"点了却被拒绝"的噪音。
- **服务端**负责权威校验：发起时你确实站在已激活的庙旁、目标确实已激活、通过原版传送门禁
  （`IsTeleportingPermittedFromPointToPoint`，挡住进出远古圣殿/中庭等封闭区域）、落点可站立。
- 传送会把**跟随者**（切斯特、宠物、猪人等）和**背包/背包外容器里的随从**一起带过去。
- 传送动作**不是 `instant`**：它走原版 `crushitemcast_trigger` 角色状态（保险库传送球
  `VAULTORBTELEPORT_MAP` 同款，wilson / wilson_client 双端都有）。点选后角色播约 0.4 秒施法动画，
  服务端在状态内执行传送；客户端状态负责 `locomotor:Stop()` + `FlattenMovementPrediction()`
  （被预测的客户端接受服务端传送位置、丢弃预测状态的标准机制）。
  > 历史教训：曾经把动作设成 `instant`（不播角色状态），结果传送后角色会自己走回原地——
  > instant 动作绕过状态机，客户端的移动预测从不会被压平，事后用 RPC 手工清 locomotor
  > 也只是治标（日志证明清理时根本没有可清的东西）。**会位移玩家的动作必须走双端 SG 状态**。
- 失败时角色会说话提示：不在庙旁 / 目标不可用 / 这里过不去 / 对面站不下人。

> 目前**骑乘状态不能传送**（带坐骑传送涉及坐骑与骑手的同步，留到后续处理）。

## 3.5.1 随身地图：怎么「买」

随身地图不是传统意义上的交易面板，而是**原版商店型科技站**（鸦年华奖品摊位 `carnival_prizebooth`
同款机制）：

1. 先上香激活任意一座土地庙；
2. 站到庙旁（`TUNING.RESEARCH_MACHINE_DIST` 内）打开**制作栏**——左下方钉栏会出现土地庙的站图标，
   或者切到「制作站」分类，能看到「随身地图」配方；
3. 材料够就点亮，点制作即可（播放递东西动作，道具直接进背包）。

也就是说：**庙 = 制作站，配方 = 商品，材料 = 价钱**，灰显/缺料提示全部是原版制作栏自带的行为。
未激活的庙不挂 `prototyper` 组件，所以站旁边也看不到这条配方。

购买后道具**永久持有、无限次使用**（无耐久、不消耗）；之后在**任意位置**按地图键，光标移到任意
已激活的庙图标旁右键，即可传送（判定：站在庙旁 **或** 背包里带着随身地图）。

- 配方材料在 `landshrine_config.lua` 的 `PORTABLEMAP_INGREDIENTS`（开发期占位值）。
- 整个功能可以用配置项「随身地图」关掉（关掉后不注册配方，但控制台仍可 `c_give` 出来）。
- 实现要点：自定义科技树必须登记进 `TechTree.AVAILABLE_TECH`（`builder.lua` 的 `CopyTechTrees`
  与 `player_classified` 的科技同步只遍历这张表，漏登记的话配方永远锁着且不报错）。
  **登记之后还要回填已有配方**：`recipe.lua:115` 在配方创建时就按当时的 `AVAILABLE_TECH` 填零，
  插入新键之前创建的原版配方里没有这个键，客户端开制作栏会直接报
  `builder_replica.lua:335: attempt to compare number with nil` 并弹「警告」退出——modmain 里已做回填。

## 3.6 材料是怎么算的（建造扣 / 拆除退）

原版这套机制是「**预扣 + 记账**」式的，确认过后是这样：

**建造**：在制作栏点下配方的那一刻就扣材料（`Builder:BufferBuild`），同时给该配方记一笔「已预付」的账；
真正落地时（`DoBuild`）因为账上已有记录，**不会再扣第二遍**。所以：

- 材料**只扣一次**，反复点同一配方也不会重复扣；
- 如果放置被拒绝（比如该地形已有庙、幽灵是红的），材料**不会丢**——它留在那笔账上，
  下次再点同一配方即可**免费落成**。

**拆除**有两条路，各自独立：

| 拆除方式 | 返还 |
|---|---|
| 锤子（以及调试用徒手拆除） | 按配方材料返还，打 5 折（`TUNING.HAMMER_LOOT_PERCENT = .5`），每种至少返 1 个。由 `lootdropper.droprecipeloot = true` 自动跟随配方 |
| 解构法杖 | 法杖自己按配方全额返还（不走 mod 的掉落表），我们只负责移除建筑 |

所以**不存在「返还两份」**：两条路互不干扰，且法杖那条路我们完全不碰掉落。

> 之所以用 `droprecipeloot` 而不是硬写 `SetLoot({...})`：前者会自动跟着配方走，
> 将来把开发期材料换成正式材料（木头/石头/干草）时，拆除返还自动同步，不会出现「配方改了、返还还是老材料」。
> 另外「锤子 5 折 / 法杖全额」是原版本身的设定差异（法杖更贵、更环保）。

## 4. 控制台调试入口

控制台按 **ESC 下面那个键**（`~`）打开；**一定要确认左边显示的是「远程：」**，否则命令只会跑在你的客户端上、碰不到服务端（按 Ctrl 切换远程/本地）。回车后控制台会自动关闭，这是原版行为。

远程执行的 `print` 只写进服务端日志、屏幕上看不到，所以下面这些命令会**同时把结果播到聊天栏**，直接看聊天栏即可。

```lua
LandShrineDebug.Summary()        -- 已登记的土地庙、占用的地形槽、同步字符串
LandShrineDebug.ActivateAll()    -- 激活全部土地庙
LandShrineDebug.RemoveNearest()  -- 拆掉离自己最近的一座（含未激活的），释放地形槽
LandShrineDebug.ClearSlots()     -- 解除全部槽位注册（本次会话内可重复建）
LandShrineDebug.TestBuild()      -- 服务端权威判定的回归测试（见下）
LandShrineDebug.TestTeleport()   -- 绕过地图界面直接传送一次（隔离"传送逻辑"与"地图 UI"）
```

**关于 `TestBuild()`**：正常游玩时，能不能建由**客户端的红绿判定**决定——幽灵变红就是不能建，这是理想的用户体验，也是我们想要的。但**服务端那份判定同样必须有**，因为它挡的是客户端根本不知道的两件事：

1. **两名玩家抢同一地形**：客机手里的占用表是上一帧同步来的，A 在沼泽建庙的同一瞬间，B 在另一片沼泽点下建造——B 的客户端以为还空着（绿色），服务端必须拦下 B，否则同一地形会出现两座庙。
2. **客机数据陈旧（刚进服同步还没到）或客户端被改过**：服务端是唯一的裁判。

而 `TestBuild()` **不绕过规则**：它只是跳过客户端那道预检，直接在服务端跑一次真实建造流程，然后把服务端的真实答复显示出来（该能建就正常建成，不能建就报拒绝原因和材料没被扣）。它存在的唯一理由是**服务端那份判定否则无法单人测试**——如果哪天 `canbuild` 写错了（比如恒返回 true），只靠客户端拦截是永远发现不了的，直到真的发生抢地形。

其他常用的原版命令（同样要「远程」才作用于世界）：

```lua
c_spawn("landshrine")               -- 直接刷一座土地庙（按当前位置取地形槽；白名单外则不占槽）
c_give("cutgrass", 40)              -- 备点材料
c_give("landshrine_portablemap")    -- 直接拿一张随身地图（跳过配方，用于测任意位置传送）
```

## 5. 测试清单

每条对应设计里的一个规则，按顺序走一遍即可覆盖：

1. **按地形建**：站在沼泽上建造 → 成功；放置时幽灵为绿色。
2. **同地形只能一座**：再去另一处沼泽 → 幽灵变红、点不下去（客户端拦住了，这是正常体验）；
   想确认服务端也会拒绝，用 `LandShrineDebug.TestBuild()` → 应返回「被服务端拒绝」，且材料前后都可用（没扣）。
3. **地形不在白名单**：在木地板/地毯/耕地（玩家铺的地皮）上 → 幽灵变红，提示「这地方不适合建土地庙」。
4. **未激活状态**：刚建好的庙是未激活（`idle_off` 姿态），右键显示「上香」。
5. **第一次上香**：右键 → 上香 → 播放激活动画并切到 `idle_on`，有音效；**不打开地图**。
6. **已激活的庙再上香**：再右键一次（仍然显示「上香」）→ 状态不变、**约 0.5 秒后地图自动打开**。
7. **拆除与槽位释放**：控制台敲 `LandShrineDebug.RemoveNearest()`（正式玩法里是锤子敲 4 下或解构法杖）→
   再敲 `Summary()`，占用槽应少一个 → 然后同一地形又能建了。
8. **持久化**：退出重进 → 庙仍是激活态；槽位仍被占用（再建同地形仍被拒）。
9. **多人同步**（若开分片/多人）：另一名玩家建造时，其客户端也应看到红/绿判定；
   一名玩家在某地形建了庙之后，另一名玩家在同一地形建造应立即被拒。
10. **调试开关**：把「调试：任意位置可建」打开 → 任意地形都能建、可重复建；关掉后恢复校验。
11. **地图图标**：上香激活一座庙 → 打开地图，该庙位置应出现图标且**穿雾可见**（可以跑到未探索区域验证）；
    未激活的庙不应有穿雾图标。
12. **地图传送**：站在已激活的庙旁 → 打开地图 → 光标移到另一座已激活庙的图标附近 → **右键** → 应传送过去、地图自动关闭、
    跟随的切斯特/宠物也一起过来。
13. **传送的两条限制**：① 站在远离任何庙的地方开地图 → 光标移到庙图标上**不应出现**传送动作；
    ② 传送到远古圣殿/中庭这类封闭区域应被拒绝并提示（如果有存档可以试）。
14. **材料**：建造后背包里干草/树枝各少 1；拆掉后（锤子或法杖）按配方返还（开发期配方是 1+1，
    `math.ceil` 保证每种至少 1 个，所以此刻看起来是全额）。
15. **购买随身地图**：站在已激活的庙旁打开制作栏 → 出现土地庙的站图标/「随身地图」配方；
    材料够时点亮，制作后背包里出现随身地图、材料扣一次。
16. **未激活不卖**：在未激活的庙旁打开制作栏 → 没有「随身地图」配方。
17. **持图任意传送**：跑到远离所有庙的地方按 M → 光标移到庙图标旁出现传送动作 → 传送成功。
18. **图丢了就失效**：把随身地图丢在地上 → 再试第 17 条 → 不再能任意位置传送（回到"必须在庙旁"）。
19. **配置项**：把「随身地图」关掉 → 配方消失；控制台 `c_give("landshrine_portablemap")` 仍可用来测传送。

> 提示：测试 21 种地形很费腿，建议配合「调试：任意位置可建」+ `c_spawn("landshrine")` 先验证逻辑，
> 再用正常流程验证一遍沼泽/草地/森林三类。

## 7. 自检脚本

本机若没有 Lua 解释器，可先跑一遍自检：

```
python tools/lua_check.py .
```

它会检查：

1. 括号配平、块关键字配对、注释/字符串是否闭合；
2. **环境规则一**：非 `modmain.lua` 的文件里不得出现 `GLOBAL` / `_G`；
3. **环境规则二**：`modmain.lua` 里不得裸用原版全局名（必须写 `GLOBAL.xxx`，
   否则裸读得到 nil、调用即崩）；
4. **原版局部名规则**：任何文件里不得裸用"原版只以 local 形式存在"的名字
   （如 `NoHoles`、`ArriveAnywhere`）——这类错误会抛 `variable 'X' is not declared`，
   而且往往发生在动作链内部，表现为玩家卡住然后掉线。

第 3、4 条靠扫描 `../原版脚本参考/scripts` 建立符号表来判定（4095 个文件；约 3.7 万个"只以 local
存在"的名字、约 4800 个原版全局名、约 100 个 mod 环境名字），结果缓存在 `tools/vanilla_symbols.json`，
之后每次运行都是秒出。原版更新后重建：

```
python tools/lua_check.py . --rebuild-symbols
```
